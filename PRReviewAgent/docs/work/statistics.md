# Task: Fix Code Review Severity Statistics for GitLab and GitHub Webhooks

## Objective

Fix the code review statistics so that Critical, Major, and Minor counts accurately reflect the **final review findings produced by Turn 2**, rather than the confidence values of issue candidates generated by Turn 1.

Focus primarily on:

- `GitLabWebhookCommentTask.cs`
- `GitHubWebhookCommentTask.cs`

Inspect directly related code, models, and utilities only where necessary.

Keep the implementation minimal and consistent with the existing architecture.

## 1. Background

The code review pipeline consists of two stages.

### Turn 1 — Issue Candidate Discovery

Turn 1 identifies potential defects and outputs structured issue candidates.

Each candidate contains a `confidence` field with one of these values:

- `high`
- `medium`

Turn 1 explicitly does not assign final severity.

Its responsibility is to identify and validate potential issues, not to decide their final reporting priority.

### Turn 2 — Final Review

Turn 2 evaluates the candidates, applies the review policy, and produces the final review comment.

The final output is organized by severity, using only the following headings:

```markdown
## Critical

## Major

## Minor
```

Turn 2 may reject, consolidate, or otherwise modify the candidate findings.

Therefore, the number of Turn 1 candidates is not necessarily equal to the number of final reported issues.

## 2. Current Problem

The existing implementation contains logic similar to:

```csharp
foreach (Prompt.Issue issue in combinedCandidates.issues)
{
    string conf = issue.confidence?.Trim() ?? string.Empty;

    if (string.Equals(conf, "Critical", StringComparison.OrdinalIgnoreCase))
    {
        fileGroupCritical++;
        fileGroupSelected++;
    }
    else if (string.Equals(conf, "Major", StringComparison.OrdinalIgnoreCase))
    {
        fileGroupMajor++;
        fileGroupSelected++;
    }
    else if (string.Equals(conf, "Minor", StringComparison.OrdinalIgnoreCase))
    {
        fileGroupMinor++;
        fileGroupSelected++;
    }
}
```

This implementation incorrectly interprets `confidence` as severity.

Because Turn 1 produces `high` or `medium`, the Critical, Major, and Minor counters do not reflect the actual review results.

Simply changing the expected values of `confidence` is not a valid fix.

## 3. Required Changes

### 3.1 Inspect the Existing Review Flow

First, examine the complete review flow in:

- `GitLabWebhookCommentTask.cs`
- `GitHubWebhookCommentTask.cs`

Identify:

1. Where Turn 1 candidates are collected and combined.
2. Where Turn 2 is invoked.
3. Where the final Turn 2 response is received.
4. Where severity statistics are calculated.
5. Where these statistics are logged, aggregated, or displayed.
6. Whether either provider already has a structured representation of final findings.

Trace relevant helper methods and data structures as necessary.

Do not assume that both webhook implementations are identical.

### 3.2 Calculate Severity From Turn 2 Results

The severity statistics must be based on the final findings produced by Turn 2.

Required counters:

```csharp
fileGroupCritical
fileGroupMajor
fileGroupMinor
fileGroupSelected
```

Their intended meanings are:

| Counter | Meaning |
|---|---|
| `fileGroupCritical` | Number of final Critical findings |
| `fileGroupMajor` | Number of final Major findings |
| `fileGroupMinor` | Number of final Minor findings |
| `fileGroupSelected` | Total number of final reported findings |

Maintain the invariant:

```csharp
fileGroupSelected =
    fileGroupCritical +
    fileGroupMajor +
    fileGroupMinor;
```

Do not calculate these counters from `combinedCandidates.issues` unless that collection has explicitly been transformed into the final Turn 2 findings.

Prefer an existing structured Turn 2 result if available.

If Turn 2 only returns Markdown, derive statistics from that final Markdown output.

### 3.3 Handle Markdown Output Correctly

If Markdown parsing is required, follow the existing Turn 2 output contract.

Recognize these severity headings:

```markdown
## Critical
## Major
## Minor
```

Count actual reported issues beneath each severity section.

Important requirements:

- Do not count severity headings themselves as findings.
- Do not count an empty severity section as one finding.
- Do not count individual paragraphs, evidence blocks, or recommendations as separate findings.
- Handle multiple findings under the same severity heading.
- Do not count rejected Turn 1 candidates.
- Do not count the same finding multiple times.
- Do not interpret severity words appearing in ordinary prose as section headings.

Inspect the actual formatting rules of the Turn 2 prompt before implementing the parser.

Use the existing issue boundaries or formatting conventions if they are sufficiently well defined.

If the current Turn 2 format does not provide reliable issue boundaries, introduce the smallest compatible formatting clarification necessary.

Avoid brittle heuristics that infer issue counts from arbitrary Markdown paragraphs or keyword occurrences.

### 3.4 Preserve the Meaning of Confidence

Keep the Turn 1 `confidence` field unchanged.

Valid values remain:

```text
high
medium
```

Do not:

- Rename `confidence` to `severity` as a workaround.
- Add severity assignment responsibilities to Turn 1.
- Require Turn 1 to predict Critical, Major, or Minor.
- Modify the Turn 1 prompt merely to accommodate the existing statistics code.

Confidence and severity describe different concepts and must remain separate.

### 3.5 Keep GitLab and GitHub Consistent

Apply equivalent behavior to both webhook implementations.

The same final review content must produce identical severity counts, regardless of whether the review was triggered by GitLab or GitHub.

If both implementations require identical parsing logic, consider extracting a small shared helper rather than duplicating the parser.

However:

- Prefer an existing shared utility when available.
- Avoid unnecessary abstractions.
- Do not refactor unrelated review orchestration.
- Preserve provider-specific behavior and comment formatting.

## 4. Aggregation and Statistics

Inspect how file-group statistics are accumulated into overall review statistics.

Ensure that severity counts are derived from the appropriate final review output and aggregated exactly once.

Check for:

- File-group-level accumulation.
- Overall review totals.
- Zero-finding reviews.
- Empty or unsuccessful Turn 2 results.
- Multiple file groups within a single review.
- Possible double counting when reviews are retried or regenerated.

Preserve the existing semantics of unrelated counters, particularly any counters representing Turn 1 candidates or processed files.

Do not silently redefine unrelated statistics.

If Turn 2 fails or produces an unparseable response, follow the existing error-handling conventions. Do not report fabricated zero findings as if parsing had succeeded.
